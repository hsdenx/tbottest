tbottest.generic¶

This is an example approach for a hopefully easy to use lab and board support.

The configuration of a board is in two files, the lab configuration (lab host, build hosts, console, power control, …) and the board configuration (the settings of the board for the testcases). Both come in one of two formats, with the same sections and keys:

  • ini files, tbot.ini and BOARDNAME.ini, read with configparser (https://docs.python.org/3/library/configparser.html, with all its limitations). Values that change from run to run are @@...@@ placeholders, which boardspecific.py replaces at every start, see boardspecific runtime adaptions (ini files).

  • JSON files, tbot.json and BOARDNAME.json. Values that change from run to run are expressions like ${flag:kasvariant:-musl}, so there is no boardspecific.py, see JSON configuration and expressions.

The flags inifile: and boardfile: (see tbot flags) name the two files, and their extension selects the format. create_setup.sh sets up ini files, or JSON files with --json.

The rest of this document calls the files tbot.ini and BOARDNAME.ini and writes a section as [SECTION], as in an ini file. With JSON these are tbot.json, BOARDNAME.json and the key "SECTION" of the top level object.

generic testcases¶

With this configuration the testcases in tbottest.tc.generic_board run without code of your own. What they check comes from keys of the board configuration (see board configuration (BOARDNAME.ini or BOARDNAME.json)), a value for one testcase only goes into its section TC_BOARDNAME.TESTCASENAME. A testcase whose key is not set is skipped.

Start them like any other testcase, e.g. with the aliases and variables of setup.sh

$ source setup.sh
$ tbBOARDNAME $tbtc.generic_board.generic_lnx_test_dmesg

The generic Linux testcases, all started by tbottest.tc.generic_board.generic_lnx_all():

requirements for lab host¶

Commands that need root rights on the lab host (setting up the board’s ethernet device, mounting an SD card, sd-mux, imx_usb, uuu, installing packages) run with sudo when tbot is logged in to the lab host as a normal user; sudo then has to work without entering a password. When tbot is logged in as root, they run without sudo, so a lab host without sudo (for example one built with Yocto) works as well. tbottest asks id -u once per machine, see tbottest.tc.common.lnx_sudo(). Use it in your own testcases instead of a fixed sudo:

from tbottest.tc.common import lnx_sudo

lab.exec0(*lnx_sudo(lab), "mkdir", "-p", path)

Commands you write into tbot.ini yourself (e.g. labinit) are run as written, so leave out sudo there on a lab host you log in to as root.

You should be able to ssh between lab host, build host and board without entering a password or something else!

configuration¶

Create a directory, e.g. tbotsetup, which holds the sources of tbot and tbottest and a subdirectory tbotconfig with all your project specific settings and testcases. The layout, file by file, is in file/directory overview; the example is tbottest/tbotconfig.

Note

You can simply use the script create_setup.sh in scripts, which will create all files and directories. Start it with the option “–inter” and you get asked some questions, which help to make a better basic setup.

$ ./scripts/create_setup.sh --inter

tbot comes from the branch v0.10.10-emb of https://github.com/EmbLux-Kft/tbot: tbot v0.10.10 with the changes tbottest needs on top, so nothing has to be patched after the clone. tbottest comes from the branch master of https://github.com/hsdenx/tbottest, another one with -b <branch>, a fixed commit with -c <commit>.

If tbot or tbottest exist already, create_setup.sh brings them to the current state of their branch: nothing happens if they are there already, a fast forward if the clone has neither commits of its own nor local changes; otherwise it only says why it left the clone alone, so no local work is lost. tbottest is not updated when it is set to a commit with -c, and neither clone is with --no-update. The environment variables TBOT_URL, TBOT_BRANCH and TBOTTEST_URL replace the sources, e.g. with a mirror.

boardspecific runtime adaptions (ini files)¶

The ini file approach is static, which means we cannot change configuration @runtime. With JSON files, use expressions instead, see JSON configuration and expressions. This generic approach searches in tbotconfig for a boardspecific.py file, which can contains several functions, the generic approach tries to call.

In this functions you can adapt settings dependend on the usecase. Or may do special stuff in machine shells.

In the default ini files there are placeholders beginning with @@ and ending with @@. You can easily replace them with helper functions.

Therefore the following functions are used:

set_board_cfg(temp: str = None, filename: str = None)¶

This file is called early in bootup before any ini file is parsed. So you can adapt the ini files for your needs

import tbot
from tbottest.generic.iniconfig import replace_in_file

tbot.selectable.printed = False

def print_log(msg):
     if tbot.selectable.printed:
            return

        tbot.log.message(tbot.log.c(msg).yellow)

def set_board_cfg(temp: str = None, filename: str = None):
    """
    setup board specific stuff in ini files before they get parsed
    """
    # print tbot.flags, as tbot prints them not longer
    print_log(f"TBOT.FLAGS {tbot.flags}")

    replace_in_file(filename, "@@TBOTBOARD@@", "<boardname in your lab setup>")
    replace_in_file(filename, "@@TBOTDATE@@", "20230221")
    replace_in_file(filename, "@@TBOTMACHINE@@", "<yocto machine name>")

    tbot.selectable.boardname = None
    for f in tbot.flags:
        if f.startswith("boardname:"):
            tbot.selectable.boardname = f.split(":", 1)[1]

    if tbot.selectable.boardname == None:
        tbot.selectable.boardname = "wandboard"

board_set_boardname¶

called from initconfig.py generic_get_boardname()

import tbot


def board_set_boardname() -> str:
    # do not use boardname flag
    BOARDNAME = "foo"
    for f in tbot.flags:
        if "8G" in f:
            if len(f) == 2:
                BOARDNAME = "foo-8G"

    return BOARDNAME

set_ub_board_specific¶

called from boardgeneric.py in init function.

setup U-Boot specific parts after entering the U-Boot shell

def set_ub_board_specific(self):
    optargs = self.env("optargs")
    optupd = False
    if "bootchartd" in tbot.flags:
        optargs = f"{optargs} init=/lib/systemd/systemd-bootchart"
        optupd = True

    if "debug_initcalls" in tbot.flags:
        optargs = f"{optargs} initcall_debug"
        optupd = True

    if optupd == True:
        self.env("optargs", optargs)

    if "silent" in tbot.flags:
        self.env("console", "silent")

JSON configuration and expressions¶

Instead of the two ini files, tbot reads the same configuration from two JSON files, if the flags inifile: and boardfile: name files that end in .json (both, mixing ini and JSON stops tbot):

-f inifile:tbotconfig/BOARDNAME/tbot.json -f boardfile:tbotconfig/BOARDNAME/BOARDNAME.json

A JSON file is an object of sections, each an object of keys, with the same names as in the ini file. A value may be a string, a number, true, false, null, a list or an object; tbot keeps it as the string the ini file would have (lists and objects as Python literal), so every testcase reads it as before.

With JSON, tbot reads the files as they are: no copies, no @@...@@ placeholders, and no boardspecific.py, which is not even imported. What depended on flags or the environment is written as an expression in the file. The expressions also work in ini files, after the placeholders are replaced:

expressions in the configuration files¶

expression

value

${env:NAME}, ${env:NAME:-default}

environment variable NAME

${flag:NAME}, ${flag:NAME:-default}

value of the tbot flag NAME:<value>, True for a flag NAME without value

${lab:key}

key of the lab section of tbot.ini or tbot.json (LABHOST or LABHOST_<labname>), in the board file

${tbot:SECTION:key}

key of SECTION of tbot.ini or tbot.json, in the board file

A value that is not set and has no default stops tbot with the expression and the file. The default is used only when the value is not set. Expressions may be nested, and are replaced before configparser interpolates ${key} and ${section:key} of the same file, so a section can be selected by a flag:

{
    "default": {
        "kasvariant": "${flag:kasvariant:-musl}",
        "kasymlname": "${KASVARIANT_${flag:kasvariant:-musl}:kasfile}",
        "nfs_path": "${lab:nfs_base_path}/${vendor}/${machine}/${kasvariant}",
        "serverip": "${tbot:IPSETUP_BOARDNAME_eth0:serverip}"
    },
    "KASVARIANT_musl": {"kasfile": "BOARDNAME-musl.yml"},
    "KASVARIANT_glibc": {"kasfile": "BOARDNAME-glibc.yml"}
}

Without the flag boardname: the board name comes from the key board of the lab section of tbot.json, e.g. "board": "${flag:boardname:-BOARDNAME}". A U-Boot variable that depends on a flag, what set_ub_board_specific() of boardspecific.py did, is an entry of ub_env with "flag", set only with that flag:

{"name": "console", "val": "silent", "flag": "silent"}

An entry with "append" or "remove" instead of "val" changes the value the variable has on the board at that point, for example after an entry with "val" before it. Both take words separated by blanks. Every word of "remove" is taken out, then every word of "append" that is not in the value yet is added at the end. A variable left empty is deleted. So several flags can each add a word to the same variable:

[
    {"name": "optargs", "val": "consoleblank=0 quiet"},
    {"name": "optargs", "append": "init=/lib/systemd/systemd-bootchart", "flag": "bootchartd"},
    {"name": "optargs", "append": "initcall_debug", "flag": "debug_initcalls"},
    {"name": "optargs", "remove": "quiet", "flag": "verbose"}
]

The testcase tbottest.tc.generic_board.generic_config_to_json() writes the configuration of a run with ini files as tbot.json and <boardname>.json, as the start of a JSON configuration (flag config_json_dir:<dir>, default config-json); with the flag config_json_resolved it writes the values resolved, to compare two configurations.

The lab configuration describes the lab host, the build hosts and how tbot reaches and controls the board. Find example files here: tbottest/tbotconfig/BOARDNAME/tbot.ini and tbottest/tbotconfig/BOARDNAME/tbot.json.

        "tmpdir": "/tmp/tbot/${username}"

setup for BDI2000 debugger¶

if your board has an Abatron BDI2000 attached, define its address. tbot then provides the BDI2000 as a machine for the role tbottest.bdi2000.BDI2000, a telnet session to the BDI’s command line from the lab host, on which exec() runs one BDI command and returns its output.

Open an interactive session on it with the testcase

tbottest.tc.bdi2000.bdi2000()

Leave it like any other interactive session, with CTRL+] three times within one second.

With poweron_cmds set, the board control runs these commands on the BDI2000 every time it has powered the board on, for example reset run when the BDI would otherwise hold the CPU in reset (tbottest.machineinit.BDI2000Cmds). Right after power on the BDI still waits for the target Vcc and a command sent then is lost; with poweron_wait_state set, the commands are only sent once the BDI command info reports that target state.

After reset the BDI works through the init list of its configuration file, but prints its prompt before it is done. A command whose output shows the init list started waits until the BDI reports it passed (and fails if it reports failed), so poweron_cmds = ["reset", "go 0x40000100"] starts the target only after the init list ran.

The BDI has no return codes and takes the next command even after one failed. exec() therefore raises an error when the output contains one of the messages in BDI_ERRORS (tbottest.bdi2000), for now Cannot open file on host, and when a load does not report Loading program file passed. The remaining poweron_cmds are not sent then, so a go after a failed load does not start whatever is in the target’s memory, and the testcase fails at once. A load of a file that is not on the TFTP server:

[bdi2000] load 0x00100000 BOARDNAME/20261001/musl/u-boot-ram.bin bin
     ## Loading BOARDNAME/20261001/musl/u-boot-ram.bin , please wait ....
     ## # Cannot open file on host

poweron_cmds can also be a dictionary of named command lists, for a board that is started in more than one way. The tbot flag -f poweron_cmds:<name> selects the list to run; without the flag the entry default is taken, and no commands at all if there is none. -f poweron_cmds:None skips the BDI2000 after power on completely, poweron_wait_state included, for example when the board is started by hand on the BDI (tbottest.initconfig.bdi2000_poweron_cmds()).

poweron_cmds = {
    "default": ["reset run"],
    "nowdt": ["reset", "go 0x40000100"],
    }

A list may contain the entry configname:<file>, the configuration file the BDI has to run with for the other commands. It is not sent as a command: before the other commands, the board control asks the BDI with config which file it runs with. If it is <file>, the commands run as usual. Otherwise it sets <file> with config <file> <host>, the host being the one the BDI loads its current file from. The BDI answers Updating configuration passed. Booting ....., boots with the new file right away and ends the telnet session; tbot connects again until the BDI answers, within poweron_timeout seconds, and checks that it runs with <file> before it waits for poweron_wait_state and sends the commands (tbottest.bdi2000.ensure_config()). So each command list can bring the configuration file it needs:

poweron_cmds = {
    "default": ["configname:BOARDNAME/bdi/BOARDNAME-nowdt.cfg", "reset", "go 0x40000100"],
    "reset": ["configname:BOARDNAME/bdi/BOARDNAME.cfg", "reset run"],
    }

board configuration (BOARDNAME.ini or BOARDNAME.json)¶

The board configuration holds the settings of the board for the testcases, in tbotconfig/BOARDNAME/BOARDNAME.ini or BOARDNAME.json (flag boardfile:). Find example files here: tbottest/tbotconfig/BOARDNAME/BOARDNAME.ini and tbottest/tbotconfig/BOARDNAME/BOARDNAME.json.

It contains the sections TC and TC_BOARDNAME, and optionally a section TC_BOARDNAME.TESTCASENAME for a testcase. While a testcase decorated with tbottest.tc.generictestdef.tc_config() or tbottest.tc.generictestdef.require_cfg() runs, a key is looked up first in TC_BOARDNAME.TESTCASENAME, then in TC_BOARDNAME and then in TC. Outside of such a testcase only the last two count. What happens if no section has the key is described at tbottest.initconfig.init_get_config().

There is deliberately no section TC_TESTCASENAME for a testcase on all boards. A value for all boards goes into TC, so a key is never searched in more than three places.

For example, the strings of the dmesg testcase for the board BOARDNAME only, as ini file

[TC_BOARDNAME.generic_lnx_test_dmesg]
dmesg = ["Linux version 6.18", "Found initrd at"]

and as JSON file

}

The class GenericBoardConfig in tbottest/boardgeneric.py holds what belongs to the board itself (tmpdir, shelltype). Its instance cfggeneric is the cfg the generic testcases in tbottest.tc.generic_board use. They read their keys when they run, with cfg.get_config(), cfg.get_config_int(), cfg.get_config_bool() and cfg.get_config_literal(), so they find their own section. ub_env groups¶

Besides ub_env, which is always set, the board ini can hold groups ub_env_<name> of U-Boot environment variables.

The tbot flag ub_env:<group>[,<group>...] selects the groups to set, for example only the network settings, so the default environment of U-Boot stays as it is otherwise. Without the flag all groups are set, as if they were one ub_env. ub_env:none sets only ub_env.

ub_env_depends names the groups a group depends on. An unknown group, in the flag or in ub_env_depends, and a cycle in the dependencies stop tbot with an error that lists the known groups. Group names are lower case, as configparser stores keys.

ub_env = [{"name":"console", "val":"ttyCPM0,115200"}]
ub_env_setip = [{"name":"serverip", "val":"192.168.3.1"}, \
  {"name":"ipaddr", "val":"192.168.3.20"}]
ub_env_fitboot = [{"name":"load_fit", "val":"tftp 1000000 fitImage"}, \
  {"name":"net_fit", "val":"run load_fit; bootm 1000000"}]
ub_env_depends = {"fitboot": ["setip"]}

With these, -f ub_env:setip sets console, serverip and ipaddr; -f ub_env:fitboot sets console, then setip, then fitboot.

ub_env_bootcmd names the groups a boot command needs, so the tbot flag bootcmd:<cmd> selects them by itself:

ub_env_bootcmd = {"net_fit": ["fitboot"]}

-f bootcmd:net_fit then sets ub_env, setip and fitboot, without a flag ub_env. With ub_env:<group> as well, both are set; ub_env:none sets only ub_env, also with bootcmd. A boot command that ub_env_bootcmd does not name leaves the selection as it is: the groups of ub_env:<group>, or all of them.

command versions¶

The output of a command depends on where it comes from. top of busybox prints other columns than top of procps-ng, busybox has devmem where a full system has devmem2. tbot finds this out with cmd_get_version(cmd) of a linux machine, once per machine, and returns a CmdVersion whose str() is <implementation>:<version>, for example busybox:1.37.0, procps-ng:4.0.6 or notfound. Testcases of tbottest use it instead of checks of their own (process measurement with top and ps, lx_devmem2_get, iperf, lnx_netcmd).

Key cmd_versions presets the answers, so tbot does not have to find them out on every run. It goes into section [LABHOST] (or [LABHOST_<labname>]) of tbot.ini for the lab host, into [BUILDHOST] (or [BUILDHOST_<name>]) of tbot.ini for the build host and into [TC] (or [TC_<boardname>]) of the board ini for the board. A command that is not in it is found out as before. A value a testcase sets with cmd_versions_set() wins over the configuration.

cmd_versions = {
    "top": "procps-ng:4.0.6",
    "devmem": "busybox:1.37.0",
    "devmem2": "notfound",
    }

One command per line works, as configparser takes every line indented deeper than the key as continuation of the value. In [TC] of the board ini template the keys are indented by four spaces, so the commands need eight. In a JSON file the value is an object:

{
    "TC": {
        "cmd_versions": {"top": "procps-ng:4.0.6", "devmem": "busybox:1.37.0"}
    }
}

The testcase tbottest.tc.generic_board.generic_cmd_versions() finds out the commands tbottest uses on the lab host, the build host (if tbot.ini has a [BUILDHOST] section) and the board and logs the line for each, ready to copy into the configuration. Run it again when the root filesystem, the lab host or the build host changes.

cmd_get_version(cmd, autoinstall=True) installs a missing command on Debian and Ubuntu (apt-get) and on Fedora (dnf), with sudo unless logged in as root. A system without a known package manager, like a root filesystem built with Yocto, keeps notfound. The tbot flag cmd_versions_install makes generic_cmd_versions install missing commands.

configuration and package installation for LinuxShell.cmd_get_version() of tbot

tbot finds out once per machine which implementation and version a command has (busybox, procps-ng, …). The generic machines of tbottest add two things:

  • key cmd_versions in the ini file presets the results, so tbot does not have to find them out on every run (section [LABHOST] or [LABHOST_<labname>] in tbot.ini for the lab host, [TC] or [TC_<boardname>] in <boardname>.ini for the board). The testcase tbottest.tc.common.lnx_cmd_versions() prints such a line, tbottest.tc.generic_board.generic_cmd_versions() for the lab host and the board.

  • cmd_get_version(cmd, autoinstall=True) installs a missing command on Debian, Ubuntu (apt-get) and Fedora (dnf). A Yocto root filesystem has no package manager, there the command stays notfound.

argumentfiles¶

it is convenient to collect tbot arguments in argumentsfile. As you will have a lot of tbot arguments. We start in this example with a base “argsBOARDNAME” file, which than other files include.

Note

You can use shell variables also in argumentfiles!

newtbot_starter.py sets TBOT_STARTTIME to the start time of the run, YYYYMMDD-HHMMSS, if it is not set already. With it, every run writes its log to a file of its own, here in log/ below the directory tbot is started from, which has to exist:

--json-log-stream
log/${TBOT_STARTTIME}.log

The following example uses piccom for accessing serial console and sispmctl for boards power control.

If you have another setup, adapt this “base” argument file accordingly.

For example, if you want to use kermit for accessing console, remove the tbot flag piccom (as kermit is default).

If you want to use Tinkerforge for controlling boards power, add flag “tinkerforge”

$ cat tbotconfig/BOARDNAME/args/argsBOARDNAME
@tbotconfig/BOARDNAME/args/argsbase
-fpicocom

Note

argsbase is a simple copy from tbottest/tbotconfig/BOARDNAME/argsfiles/argsbase

With executing tbot on lab host, you do not need to ssh to lab host, so use local flag.

$ cat config/BOARDNAME/args/argsBOARDNAME-local
@config/BOARDNAME/args/argsBOARDNAME
-flocal

If you do not want that tbot always initialize ethernet configuration on your lab host, use

$ cat config/BOARDNAME/args/argsBOARDNAME-local-noeth
@config/BOARDNAME/args/argsBOARDNAME-local
-fnoethinit

If you want to login to a board, which is already on and runs linux

$ cat config/BOARDNAME/args/argsBOARDNAME-local-noeth-on
@config/BOARDNAME/args/argsBOARDNAME-local-noeth
-falways-on
-fnouboot
-fnopoweroff

Note

start tbot with flag “always-on” and tbot will not poweroff the board when ending, so if you have bootet into linux, and logout, linux will remain and tbot can logon again!

This helps a lot when developing testcases!

Argumentfile for ssh login¶

If you want to login per ssh into an already running linux on the board

$ cat config/BOARDNAME/args/argsBOARDNAME-local-noeth-on
@config/BOARDNAME/args/argsBOARDNAME-local-noeth
-fssh

And last but not least, if you have an imx6 based board and want to load SPL/U-Boot with tbot onto it, start tbot with:

$ cat config/BOARDNAME/args/argsBOARDNAME-local-uuu
@config/BOARDNAME/args/argsBOARDNAME-local
-fuuuloader

tbot flags¶

The generic lab and board approach defines some tbot flags, so tbot can handle different usage challenges. It is recommended to collect arguments in so called argumentsfiles, else you are lost in tbot flags…

Description

always-on

board is already on, log into linux

boardfile

format boardfile:<path>, the board configuration, an ini file or, if the name ends in .json, a JSON file, relative to the tbotconfig directory or absolute; default the BOARDNAME.ini template

format boardname:<name>, name of the board, used when boardspecific.py does not define board_set_boardname()
